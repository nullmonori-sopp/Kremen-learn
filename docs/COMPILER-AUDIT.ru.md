# Аудит интеграции Kremen 0.4.6

[English](COMPILER-AUDIT.md) · [Платформы](PLATFORMS.ru.md) · [Запуск](EXECUTION.ru.md)

## Исходная версия

Репозиторий: <https://github.com/nullmonori-sopp/Kremen>.
Используется коммит **671140cd1ef4ea453a07047df07c945efa7184e2**, файл
`VERSION`: `0.4.6`. При проверке теги релизов отсутствовали. Коммит закреплён
в `toolchain.lock.json`, полная копия исходников с оригинальной MIT-лицензией
находится в `vendor/kremen/`.

Приложение использует полный компилятор на C11, а не меньший self-hosted subset.
`make` создаёт `build/kremen`; версия сообщает `Kremen 0.4.6 (native C11)`.
На Linux x86-64 по умолчанию используется ассемблерная функция копирования;
`make USE_ASM=0` выбирает реализацию на C.

Kremen генерирует C. Для сборки программ нужны C11-компилятор, заголовки libc,
линкер и POSIX threads. Стандартные флаги: `-std=c11 -Wall -Wextra -Wpedantic
-Werror -O3 -pthread`. Наличие одного `kremen` ещё не означает готовность backend.

## Настоящие команды

| Действие | Команда upstream | Значение |
| --- | --- | --- |
| Проверка | `kremen check main.kr --root DIR --mode=learn --diagnostic-format=json` | Проверяет язык без C-компилятора |
| Сборка | `kremen build main.kr -o app --mode=work --diagnostic-format=json` | Создаёт исполняемый файл через C |
| Запуск | `kremen run main.kr --mode=learn` | Работает в upstream; приложение может отдельно собрать и запустить с разными лимитами |
| Генерация C | `kremen emit-c main.kr -o main.c --mode=work` | Включает исходник runtime в результат |
| Форматирование | `kremen fmt main.kr` | Печатает текст; `-w` записывает, `--check` проверяет |
| Объяснение | `kremen explain E110` | Работает офлайн; `--list` показывает каталог |

Флаги `--mode=work` и `--mode=learn` существуют. При повторении применяется
последний. `fmt` и `explain` отвергают `--mode`: семантический профиль там не
выполняется. Точное имя JSON-флага: `--diagnostic-format=json`. Режим хранится
как настройка приложения и передаётся каждой проверке; постоянного файла
профиля компилятора нет.

Оба режима сохраняют проверки типов, заимствований и безопасности runtime.
Learn добавляет `L001` явную инициализацию, `L002` обработку результатов,
`L003` использование кодов ошибок, `L004` явные варианты match и `L005`
ввод целого числа с результатом. Это не доказательство завершения программы.

## Диагностика и координаты редактора

При ошибке frontend пишет один JSON-объект в stderr и завершает команду
неуспешно. Успешный `check` печатает обычное `path: OK` в stdout. Компилятор
останавливается на первой ошибке frontend. Сообщения C-backend, runtime и часть
поздних ошибок ОС остаются обычным текстом и должны быть видны пользователю.

Основные поля: `kind`, `code`, `message`, `file`, `line`, `column`,
`end_line`, `end_column`, `offset`, `length`, `hint`, `explain`, `mode`,
`related`, `imports`. Конец диапазона не входит в него. `offset` и `length`
считают байты UTF-8; строка и столбец начинаются с единицы, столбец тоже
считает байты. Табуляция — один байт. `excerpt`, `caret`, `underline_width`
описывают отображение, могут быть обрезаны и не подходят для координат Monaco.

Monaco считает кодовые единицы UTF-16. Адаптер использует оригинальный текст,
границы UTF-8, число переводов строк до смещения и длину UTF-16 после последнего
перевода строки. Табуляция остаётся одним символом модели. Оригинальный JSON
и текст сообщения сохраняются.

Проверенный пример:

```go
func main() {
	println("Привет 🪨"); println(missing)
}
```

Kremen выдаёт `E107`: строка 2, байтовый столбец 40, `offset: 53`, `length: 7`.
Правильный диапазон Monaco: строка 2, столбцы **32–39**, а не 40–47 и не caret
33 из фрагмента. `kremen explain E107` объясняет категорию ошибки офлайн.

## Файлы, import и runtime

Проекты используют `.kr` и необязательные парные `.krh`. Import разрешается
относительно импортирующего файла и ничего не скачивает. Импортируется реализация
или каталог модуля, не заголовок. `--root` должен содержать канонический entry
и все исходники. Циклы и выход через символьные ссылки отклоняются. Это правило
загрузки исходников не ограничивает файловую систему запущенной программы;
для неё приложение создаёт отдельную изоляцию ОС.

`build`, `run`, `emit-c` требуют `runtime/kremen_rt.h`. Поиск относительно
исполняемого файла включает `../share/kremen/runtime/kremen_rt.h` и
`../runtime/kremen_rt.h`. Комплект приложения: `toolchain/bin/kremen` рядом
с `toolchain/runtime/kremen_rt.h`. `check`, `fmt`, `explain` обходятся без
этого заголовка. Встроенный каталог содержит 45 категорий, включая `E015`
и `L001–L005`.

Коды `readIntResult()` принадлежат отдельной области: 1 EOF, 2 неверное целое,
3 выход за i64, 4 ошибка потока. Это не OS `errno`. Файловые и потоковые
операции используют коды ОС; именно для них подходит `errorMessage`.

## Фактические проверки

В этой среде компилятор собран и запущен на Linux x86-64 с GCC. Проверены
check/learn, build `-O0`, исполнение бинарного файла, emit-c, fmt, explain,
JSON-диагностика и пример с Unicode/табуляцией. Повторно запущенные тесты
upstream перечислены в [протоколе проверок](VERIFICATION.ru.md).

836 проверок из документа upstream — результаты его релиза, а не автоматически
результаты этой сессии. Не заявляются сборка Windows, повторный прогон
санитайзеров или исчерпывающая проверка языка.
